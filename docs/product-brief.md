## V1 scope

Routes: `/`, `/work`, `/work/resume-analyzer`, `/work/notification-platform`, `/work/user-management-api`, `/changelog`, and a useful 404. Homepage flow: hero → selected work → engineering approach → experience → short personal story → contact → version/changelog footer.

Each case study covers problem, personal contribution, implementation, architecture, decisions, tradeoffs, current limitations, stack, and reviewed source/demo links. Public project text must remain readable without JavaScript. Missing assets or later-phase sections must not create fake downloads, empty actions, or dead navigation targets.

## Technical direction for later planning

One Next.js App Router application, strict TypeScript, Tailwind CSS with semantic tokens, typed local content, and local Markdown/MDX for long case studies. Use npm and commit its lockfile. Select compatible stable package versions during feature planning/implementation and record actual versions in [toolchain](toolchain.md); no application packages are selected or installed yet.

Prefer server rendering and small client components. Author exact diagrams in SVG/HTML, use CSS transitions first, and justify any animation dependency. No database, authentication, CMS, contact email service, portfolio LLM, or runtime GitHub API dependency is needed for V1. Contact uses a verified email link and copy action with a usable failure fallback.

Future content records distinguish `draft`/`published`, verified source URL, optional checked demo URL, evidence references, checked date, and limitations. Exclude drafts from indexes, generated routes, metadata, and sitemap; draft and unknown slugs return 404. Internal provenance belongs in planning records unless useful to a visitor.

Record actual checks and performance measurements with environment and limits; automated checks alone do not prove conformance.
